# LaTSEC: implementation

Two independent research implementations of **SEC** (expander-code secret sharing
over the integers) and **LaTSEC** (a three-round lattice threshold signature with
identifiable abort), following the paper and the SEC paper it builds on (cited
below as [46], its number in the paper's bibliography):

- [`latsec-rs/`](latsec-rs): Rust, the performance and measurement implementation,
  with a command-line front end.
- [`latsec-py/`](latsec-py): Python, the readable test-vector generator, organized
  by the sections of the paper.

Sections, tables, figures and appendices named without a source are those of the
paper. The submitted paper and its full version number Sections 1 to 8, Tables 1
to 7, Figure 1 and Appendices A to F alike; the later appendices are in the full
version only and are cited as such.

Both read the same profiles and agree byte for byte on every test vector. They are
correctness references, not hardened implementations:

- Arithmetic and sampling are variable-time. Secret buffers are erased on a
  best-effort basis only (Rust) or not at all (Python).
- Key generation is by a trusted dealer, and all parties run in one process.
- Running them adds no security evidence. The author profiles carry the paper's
  parameters and the paper's lattice estimates, nothing more.

The algorithms are those of Figure 1 and of the full specification (Appendix I of
the full version). Section 8, Appendix F and the extended benchmarks (Appendix P
of the full version) report the measurements recorded in [`results/`](results).

## Layout

| Path | Content |

## Prerequisites

The checks and all measurements need only the first three items.

| Software | Version | Needed for |
|---|---|---|
| Rust with Cargo | 1.85 or later (required by the pinned `zeroize` crate); the recorded measurements used 1.100.0, the only version tested | `latsec-rs`. The first build downloads the crates pinned in `latsec-rs/Cargo.lock` from crates.io |
| Python | 3.10 or later; tested with 3.13 and 3.14 | `latsec-py` and `tools/` |
| PyCryptodome | 3.19 or later (`pip install pycryptodome`, or the Debian package `python3-pycryptodome`) | SHAKE256 in `latsec-py` |
| GNU Make, a POSIX shell, `taskset` (util-linux) | any recent | `make check`; `tools/run_benchmarks.sh` |
| NumPy | 1.24 or later | optional: `latsec-py/matrix_check.py --spectral` |
| SageMath | 10.7 (the notebooks); 10.9 was used for `tools/latsec_estimates.py` | optional: the notebooks in `../parameter-search`, `tools/gen_recon_fixtures.py`, `tools/latsec_estimates.py` |
| lattice-estimator | commit `27a581b` of <https://github.com/malb/lattice-estimator> | optional: the security estimates of Section 7.2 |

Everything was run on Linux on x86-64 (Debian). The code has no platform-specific
parts, but the environment record of `latsec measure` reads `/proc` and `/sys` and
is empty elsewhere. No special hardware is needed: `make check` takes one to three
minutes including the first build, `make check-full` about 15 minutes, and the
whole tree is 2 MB before building (about 1 GB with Cargo's build output).

## Build and test

```sh
make check          # both implementations, about 3 minutes
make check-full     # adds every test vector in Python and the slow checks
make vectors        # regenerate profiles/ and fixtures/kat/ with the Rust CLI
make clean          # build output and caches of both implementations
```

`make check` runs the Rust tests, `clippy` and `rustfmt`, the Python unit tests,
the Python re-derivation of every profile, and the Python generator against the
small test vectors and one author vector. The Rust side alone:

```sh
cd latsec-rs
cargo build --release
cargo test                               # about 15 s
cargo test --release -- --ignored        # n = 60 matrix constants, about 40 s on 28 cores
```

The Rust build needs neither Python nor SageMath, and does not read the notebooks.
The Python implementation needs `pycryptodome` (and `numpy` for the spectral matrix
check); see [`latsec-py/README.md`](latsec-py/README.md). Both read `profiles/` and
`fixtures/`. The notebooks in `../parameter-search` are only needed to regenerate
the matrix fixtures.

## Command line

```sh
L=latsec-rs/target/release/latsec
$L profiles build                        # regenerate profiles/*.json
$L profiles check profiles/*.json        # validate; print bounds and security-side checks
$L demo --profile profiles/author-n40-k128-nov2026.json
$L measure --profile profiles/author-n60-k256-nov2026.json --sessions 100 --json out.json
$L recon-stats --matrix fixtures/author/G-40-19-3.json --sizes 26..40 \
    --samples 100000 --beta 5 --omega 25
$L recon-compare --matrix fixtures/author/G-60-39-3.json --reference bulk.json
$L matrix-check --matrix fixtures/author/G-60-39-3.json --spectral yes
$L kat                                   # regenerate fixtures/kat/*.json
```

Party indices are zero-based on the command line and in the code; party `i` of the
paper is index `i - 1`. With `--seed TEXT` all randomness is derived from the text,
which makes a run reproducible and its keys public.

The other tools are run from the repository root:

```sh
python3 latsec-py/params.py              # Tables 4 and 5 at 60 digits; standard library only
python3 tools/extract_fixtures.py        # fixtures/author from the notebooks (read as data)
python3 tools/bench_tables.py            # the tables of Appendices F and P (full version) from results/
sage -python tools/gen_recon_fixtures.py # fixtures/sage with the SageMath pipeline of [46]
sage -python tools/latsec_estimates.py --estimator <lattice-estimator checkout>
```

## Profiles

A profile fixes everything the protocol needs and records what may be claimed for it.
Real-valued inputs are stored as dyadic rationals, all bounds are derived from them
in integer arithmetic, and loading a profile recomputes them and its digest.

| Profile | Category | Purpose |
|---|---|---|
| `functional-n10-d16`, `functional-n20-d16` | functional | Small exhaustive tests. No security claim |
| `functional-n20-d512` | functional | Full degree, 66-bit modulus, 66-bit response coefficients, 20 parties. No security claim |
| `author-n{40,60}-k{128,192,256}-nov2026` | author | The six parameter sets of Tables 4 and 5 on the matrices of Table 3 |
| `variant-n{40,60}-k{128,192,256}-q{bits}` | author-variant | The same widths and bounds with the modulus one bit shorter (Section 7.2). A variant, not a parameter set of the paper |
| `sec-only-n{40,60}-k128-q32` | sec-only | The standalone SEC sets of [46] at `q = 2^32 - 10239`. Privacy-only; signing is disabled |

## Choices the implementations make

Section 8.1 summarizes these; each is fixed here and covered by the profile digest.

- **Session message.** As in Figure 1, the signed message
  `msg` canonically encodes `(sid, act, lambda_act)` and the payload, and every
  signer evaluates the predicate `P` on it with exact integer checks. The initiator
  computes `lambda_act` with the reconstruction algorithm below; any vector that
  passes `P` is accepted.
- **Reconstruction algorithm (`xlatsec-recon-v1`).** Row-HNF witness, the unique HNF
  kernel basis, an exact integral LLL with `delta = 99/100` and fixed conventions,
  exact Babai with ties toward `+inf`, greedy refinement with `passes = window = 2`.
  The output is a mathematical function of the signer set. It usually, but not
  always, equals the vector of the SageMath pipeline of [46] (see below).
- **Hashing.** SHAKE256 with length-framed inputs and one domain string per use.
  Hashes take a key digest that covers the profile digest. `H_c` maps into the
  challenge set directly: the SHAKE256 stream feeds an unbiased fixed-weight shuffle,
  so with SHAKE256 as a random oracle `H_c` is a random oracle into `C` (Sections
  3.1 and 8.1).
- **Sampler.** The discrete Gaussian sampler of Canonne, Kamath and Steinke in exact
  integer arithmetic. Its only approximation is that proposals of magnitude `2^126`
  or more are rejected, which puts the output within statistical distance
  `exp(-2^48)` of `D_{Z, sigma}` for every supported width; the remaining
  machine-integer counters overflow with probability below `exp(-2^128)`. It is
  variable time.
- **Encoding (codec version 3).** Little-endian at the bit and byte level. Residues
  mod `q` at `ceil(lg q)` bits; the challenge as the rank of its support in the
  combinatorial number system plus sign bits, `b_c = ceil(omega_c + lg binom(d,
  omega_c))` bits as in Section 7.3; Gaussian components Golomb–Rice coded. The
  Rice parameter of shares and partial responses is fixed by the profile, the
  largest `k` with `1.2863 * 2^k <= sigma`. That is the large-width limit of the
  expected-length optimum; for every stored profile it gives the lowest computed
  length in a discrete-Gaussian model of each component, with every width at
  least 4% from a switch point ([`tools/rice_parameters.py`](tools/rice_parameters.py)). A signature carries its
  own parameter, the one that gives the shortest code. Decoders are strict, so every value has one encoding,
  and they reject an input longer than any valid encoding before reading it.
- **Signing budget.** Each signer enforces `q_participate = floor(Q_Sign / n)`
  sessions per key and never reuses a session identifier.

## Measured results

Recorded in [`results/`](results); Section 8, Appendix F and Appendix P of the full
version report them. The
records of 16 November (`20261116-measure-*`, with the table rows in
`20261116-bench-tables.txt`) are the ones in the paper; the earlier timing records
(`20261108-measure-*`) are from another machine and an earlier build. In short:

- Honest sessions on all six author profiles complete and verify (600 sessions at
  the signing threshold, 960 over all measured sizes); no honest partial response
  was rejected.
- Encoded sizes match the ideal sizes of Table 5: at `n = 60`, `kappa = 128` a
  share takes 14.32 KiB (Table 5: 14.27) and a partial response 35.96 KiB (36.13).
  Signatures average 37.84 KiB, below the 42.62 KiB of Table 5, which is computed
  at the worst-case bound `B2`.
- The reconstruction vector equals the SageMath pipeline's in 99.87% (`n = 40`) and
  99.79% (`n = 60`) of 5,237 and 5,254 authorized sets, and authorization agrees on
  all of them.
- Over 1.1 million sets per matrix, the vectors reach `|lambda|_inf = 5` and weight
  26 at `n = 40`, and `|lambda|_inf = 9` and weight 44 at `n = 60`. The paper's
  enforced bounds are `(5, 25)` and `(9, 45)`: for one authorized set of 27 parties
  at `n = 40` the Algorithm 1 vector fails the predicate. The SageMath pipeline
  returns the same vectors for these sets. Other vectors for that set pass the
  predicate (11,051 found, the lightest of weight 12; `latsec-py/alternatives.py`),
  so the initiator can supply one (Section 8.2).

## Reproducing the results of the paper

Run the commands from this directory after `cargo build --release` in `latsec-rs`;
`L` stands for `latsec-rs/target/release/latsec`. Every command prints its result;
the recorded output it is to be compared with is named in the last column. All
randomness is derived from the seeds given, so counts, sizes and norms are
reproduced exactly on any machine. Running times depend on the machine.

| Result in the paper | Command | Time | Recorded output |
|---|---|---|---|
| Tables 4 and 5: widths, bounds, primes, sizes; the smoothing margins of Sections 7.1 and 7.2 | `python3 latsec-py/params.py` | seconds | exits with status 0 and prints `ALL CHECKS PASSED` |
| Table 3: matrix constants, `n = 40` | `$L matrix-check --matrix fixtures/author/G-40-19-3.json --spectral yes` | 1 s | the printed constants against Table 3 |
| Table 3: matrix constants, `n = 60` | `(cd latsec-rs && cargo test --release -- --ignored)` | 1 min | the test passes |
| Section 7.1: `10^5` signer sets per size, `n = 40` | `$L recon-stats --matrix fixtures/author/G-40-19-3.json --sizes 26..40 --samples 100000 --seed 20261106 --beta 5 --omega 25 --json out.json` | 15 CPU-minutes | `results/20261106-recon-stats-n40.json` |
| the same, `n = 60` | `$L recon-stats --matrix fixtures/author/G-60-39-3.json --sizes 46..60 --samples 100000 --seed 20261106 --beta 9 --omega 45 --json out.json` | 30 CPU-minutes | `results/20261106-recon-stats-n60.json` |
| Section 7.1: every set of `k_c^det` parties is admissible, and one size below is not, `n = 40` | `$L recon-stats --matrix fixtures/author/G-40-19-3.json --sizes 34..35 --samples 6000000 --seed 20261106 --beta 5 --omega 25` | 1 CPU-hour | `results/20261106-kcdet.log`, `results/20261106-kcdet-n40.json` |
| the same, `n = 60` | `$L recon-stats --matrix fixtures/author/G-60-39-3.json --sizes 55..56 --samples 6000000 --seed 20261106 --beta 9 --omega 45` | 3.5 CPU-hours | `results/20261106-kcdet.log`, `results/20261106-kcdet-n60.json` |
| Section 7.2: lattice estimates | the notebook in `../parameter-search`, or `sage -python tools/latsec_estimates.py --estimator DIR` | about 15 minutes | `tools/results/20261106-estimator-*.json` |
| Section 8.1: the Golomb-Rice rule (0.17 bits, 4%) | `python3 tools/rice_parameters.py` | seconds | `tools/results/20261108-rice-parameters.txt` |
| Section 8.2: the 27-party set and its 11,051 other vectors | `python3 latsec-py/alternatives.py fixtures/author/G-40-19-3.json --rejected-notable --beta 5 --omega 25` | seconds | `results/20261108-rejected-set-alternatives.log` |
| Sections 8.2 to 8.4, Table 6, Table 7 (Appendix F), Appendix P of the full version | `tools/run_benchmarks.sh myrun [CPU]` and then `python3 tools/bench_tables.py --prefix myrun` | 15 minutes | `results/20261116-measure-*`, `results/20261116-bench-tables.txt` |
| Agreement of the two implementations on every test vector | `make check-full` | 15 minutes | every line `OK` |

`recon-stats` uses all cores by default (`--threads N`); the CPU times above are
totals. With at most `--samples` sets of a size it enumerates all of them, which is
how the two exhaustive runs are specified.

**The benchmark records.** `tools/run_benchmarks.sh` runs `latsec measure` for
the six parameter sets at three signing-set sizes, on one pinned core, with the
seeds of the recorded runs. The optional second argument is the number of the core
to pin to, as `taskset -c` takes it. Without it the script picks one itself: among
the cores the process may run on, one with the highest maximum frequency, and not
core 0 if there is a choice; it prints which. Give the argument to choose another,
for instance an isolated core. If `taskset` is missing the runs are not pinned, and
the script says so. The recorded runs used core 2 of the machine named in the
records. In a rerun, every field of a record except the times
and the environment equals the recorded one: the signer sets drawn, how many were
refused, the reconstruction-vector statistics, the norm ratios and the encoded
sizes. The times will differ; the records name the machine they were taken on
(`environment` in each JSON file), and Appendix P of the full version describes the
method. The sizes
of Table 6 are the `bytes` fields of the records at the signing threshold, also
printed in each `.log` under "encoded sizes".

**What is not reproduced here.** The parameter selection itself and the
enumeration behind `gamma_kp` are in the notebooks of `../parameter-search`, which
need SageMath; this directory re-derives the selected widths and re-checks the
matrix constants from the matrices. The reference vectors in `fixtures/sage` were
produced with SageMath by `tools/gen_recon_fixtures.py`.

## Not implemented

Distributed key generation, a network transport, constant-time arithmetic and
sampling, certified (interval) bounds on the matrix constants, independent instance
generation ([46, Algorithm 2]), and persistence of signer state.
